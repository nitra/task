## Огляд

Owner-бекенд дає frontend-у owner-вікна fail-safe командний доступ до лісу задач mt-core: сканує вузли, готує plan-review: approve/reject, фіксує прийняття роботи людиною через human_done, веде локальну ідентичність, автономію, ескалації та нагадування, а також створює чернетки планів декомпозиції M1-плановика через draft_plan. Він існує як межа між рішеннями людини в owner-вікні та файловим контрактом задач, не запускаючи агентів і не виконуючи роботу app-рівня.

## Поведінка

`run` підіймає Tauri-бекенд owner-вікна, реєструє команди, HTTP/opener-плагіни та спільний стан watcher-а. Після цього frontend працює з лісом задач через команди: `get_project_paths` і `set_project_paths` керують локальним списком коренів, `find_all_tasks_dirs` знаходить у них робочі директорії задач, а `scan_tasks` повертає актуальну read-модель вузлів з урахуванням worktree-оточення.

Створення й зміна задач ідуть через файловий контракт mt-core. `create_task` додає новий вузол, `draft_plan` записує наступну immutable-чернетку декомпозиції після перевірки children, `plan_review_info` дає frontend-у матеріал для рішення, `spawn_approve` матеріалізує затверджений план, а `spawn_reject` фіксує відмову з причиною. `read_task` постачає текст контракту для перегляду й критики, `human_done` фіксує прийняття роботи людини та запускає підняття стану вгору по композиції.

Власність і автономія є локальним шаром owner-застосунку поверх mt-core. `scan_owners` читає owner-розмітку з `autonomy.yml`, `get_identity` і `set_identity` тримають поточний handle поза git, а `write_autonomy` змінює політику лише після валідації та перевірки права власності. `read_autonomy` повертає власну політику вузла або порожній текст, якщо файл відсутній, щоб frontend міг показати успадкування без створення зайвого стану.

Write-дії у розміченому лісі працюють fail-closed: без відповідної ідентичності або з чужим effective owner зміна відхиляється. Нерозмічений ліс зберігає single-owner поведінку, а вузол поза розміченими піддеревами лишається доступним, щоб осиротілі гілки не блокувалися назавжди.

`delegate` поєднує зміну виконавця з межовою owner-розміткою: людське делегування записує прапор виконання і власника, агентне — залишає гілку без людського owner. Уся перевірка відбувається до запису, тому некоректний envelope або відсутній обов’язковий owner не лишають часткового стану.

`Escalation` описує app-рівневу ескалацію, яка не змінює derived state mt-core. `escalate` створює immutable записку вгору від поточної ідентичності до адресата, `scan_escalations` збирає відкриті й закриті ескалації для маршрутизації черги, а `resolve_escalation` фіксує рішення адресата. Відкрита ескалація переходить у чергу того, хто має вирішити, і зникає з черги автора.

Персональний ритм нагадувань не потрапляє в git: `get_snoozes` читає активні відкладення для поточної ідентичності, `snooze_reminder` записує локальне приглушення конкретного нагадування. Deadline-и задач при цьому не змінюються.

`watch_tasks_dirs` стежить за файловими змінами у tasks-директоріях і надсилає подію зміни, після якої frontend сам дебаунсить і повторно викликає сканування. Кешування в цьому бекенді немає: джерелом істини лишаються файли задач, локальний конфіг застосунку та поточний стан watcher-а.

## Публічний API

- create_task — Вузол-ціль для декомпозиції: штатний шаблонний контракт mt-core.
- scan_owners — `owner:`-розмітка воркспейсу одним проходом ФС — сировина scope-деривації на фронті (порожня мапа = нерозмічений ліс, single-owner поведінка).
- get_identity — Handle власника застосунку (None — «Хто ти» ще не пройдено).
- set_identity — Зберігає handle власника у локальний конфіг (PII лишається поза git).
- get_snoozes — Активні snooze нагадувань поточної ідентичності (id → until, ISO 8601). Персональний ритм — локально, не в git (M7, спека 260714 п. 12).
- snooze_reminder — Глушить нагадування до `until` для поточної ідентичності (fail-closed без неї). Snooze діє лише в мене — deadline у git не чіпається.
- read_autonomy — Власна політика вузла (порожній рядок — файлу немає, повне успадкування).
- write_autonomy — Пише власну політику вузла після валідації (fail-closed: битий рядок — відмова без запису).
- draft_plan — Чернетка плану декомпозиції від плановика: наступний immutable `plan_NNN.md` (`## Context` / `## Children` / `## Risks`). Children валідуються парсером mt-core ДО запису (fail-closed) — вузол одразу переходить у derived-стан plan_review і потрапляє в чергу рішень.
- read_task — Текст контракту вузла (task.md) — сировина дайджесту семантичного критика.
- plan_review_info — Read-модель plan-review: актуальний план вузла з розібраними `## Children`.
- spawn_approve — Вердикт власника: approve плану → валідація + матеріалізація дітей.
- spawn_reject — Вердикт власника: reject плану з причиною → plan-rejected_NNN.md.
- human_done — Вердикт власника «прийнято як виконане»: fact (якщо ще немає) + done із прогоном `## Check` і composite-агрегацією вгору.
- Escalation — Ескалація вузла (M6, спека 260714): immutable `escalation_NNN.md` — «записка вгору» від власника гілки замовникові вузла; розвʼязання — парний `escalation-resolved_NNN.md`. Derived state mt-core не змінюється: маршрутизація черги деривується з цих файлів на app-рівні.
- scan_escalations — Ескалації воркспейсу одним проходом ФС — сировина маршрутизації черги (відкрита ескалація зʼявляється у черзі адресата і зникає з черги автора).
- escalate — Ескалація вгору (M6): власник гілки вичерпав свої опції і передає рішення замовникові. Записка (`## Reason`) обовʼязкова — fail-closed без неї: голий факт без «що я спробував» провокує rubber-stamping або мікроменеджмент. `from` — ідентичність застосунку, не параметр.
- resolve_escalation — Вердикт замовника по ескалації: immutable `escalation-resolved_NNN.md`. Розвʼязати може лише адресат (`to`) — це його рішення, не власника гілки.
- delegate — Атомарний акт делегування (M6, оргнапрям-агностичний): виконавчий прапор (`h.md` людині / `a.md` машині — штатний механізм mt-core) + один `autonomy.yml` межового вузла (`owner:` для людини + конверт автономії). Уся валідація — до першого запису (fail-closed).
- watch_tasks_dirs — Стежить за лісом і шле `mt-changed`; frontend дебаунсить і перескановує.
- scan_tasks — знаходить task-директорії в налаштованих проєктних шляхах і повертає їх як список доступних задач.
- find_all_tasks_dirs — обходить передані проєктні шляхи та збирає всі директорії, що відповідають структурі task.
- get_project_paths — повертає поточний список шляхів, у яких застосунок шукає задачі.
- set_project_paths — зберігає новий список проєктних шляхів для подальшого пошуку задач.
- run — запускає сканування задач і виводить знайдені результати для користувача.

## Гарантії поведінки

- Перехоплює помилки і не пропускає винятків назовні (fail-safe).
- За певних помилок повертає порожнє значення (напр. `null`) замість винятку.
